# ZipZap 0.2.0-beta.1 — candidate

**Unpublished candidate.** This document describes the prepared daily-use beta,
not an available or fully qualified release. Only `0.1.0-beta.1` is published.
[العربية](0.2.0-beta.1.ar.md) · [Qualification record](../development/DAILY_USE_QUALIFICATION.md)

## Changes since the first beta

- Keep live and saved state consistent when saves fail, upgrade saved state
  transactionally, and reconcile interrupted publication using verified file
  identity and hashes without replacing existing output.
- Classify download failures, respect bounded retry delays, suggest safe server
  filenames, and require explicit decisions when replacing expired links.
- Save one queue's priority and Start/Hold state. Schedule future local-time
  windows while the app runs; missed starts and restart catch-up are skipped.
- Preview batches, select multiple downloads, customize filename categories and
  suggested folders, and save appearance, sort and column preferences.
- Opt into close-to-tray and count-only notifications. Default close still
  checkpoints and quits. Scheduling does not wake a sleeping or stopped computer.
- Distinguish browser receipt, app enqueue and rejection with protocol v2.
  Keep the existing explicit Chrome/Edge handoff and minimal extension permissions.
- Preserve Internet-zone metadata on new Windows downloads; show a warning when
  explicit Open cannot verify it. Export an explicit, bounded support summary
  containing counts/codes rather than private URLs, names or paths.

These features are implemented in development source. Their historical automated,
native and maintainer-reported checks remain distinct from the candidate gates
in the qualification record. No adaptive segmentation, higher connection cap or
large-list rewrite was introduced by the performance study.

## Upgrade and verify

Target: **Windows 11 x64, local NTFS, WebView2**. Other operating systems,
Windows 10 and ARM remain unverified. The browser package remains an unpacked
extension, with numeric version `0.2.0`, not a browser-store release.

Close all ZipZap instances before making a coherent private backup of the old
app state. Keep completed files and recoverable partials. State upgrades to
schema 5; older binaries reject it. Use the compatible newer binary or restore a
coherent pre-upgrade backup with the app closed. Never lower `user_version` or
copy a live SQLite main file separately from its journal/WAL.

Candidate distribution is **unsigned**. Compare the actual setup executable's
SHA-256 with its accompanying `SHA256SUMS.txt` before opening it. No Authenticode
publisher identity, SmartScreen reputation or automatic update is promised.
The candidate's installer upgrade/repair/uninstall/reinstall and native/browser
matrix must pass before release approval. Publication requires a separate
maintainer instruction after review of the final artifacts and evidence.

## Limits

- Safe resume may restart if representation identity cannot be established.
  Existing destination files are never overwritten. Hard links and up to twice
  the payload size in temporary space may be needed.
- Schedule windows apply only while the app runs, including explicit tray mode.
  There is one queue; no OS wake, shutdown automation or background service.
- Local history stores private URLs under normal per-user Windows permissions.
  Support exports are explicit and nothing uploads automatically.
- Cookies, authenticated sessions, media extraction, automatic browser capture,
  Firefox/store distribution, torrents and cloud sync remain outside this beta.
- Loopback throughput and sampled resource observations do not establish WAN
  results, IDM superiority or precise cold-start latency. Missing raw cold-start
  evidence is recorded in #46. No physical power-loss/full-disk test, independent
  penetration test or screen-reader certification is claimed.
