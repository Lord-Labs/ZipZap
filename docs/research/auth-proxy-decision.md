# Authenticated downloads and proxies decision (#49)

Decision date: 2026-10-23; [issue #49](https://github.com/Lord-Labs/ZipZap/issues/49). This is the M7 decision study, not an authenticated-download implementation or release claim.

## Decision

**No-go for adding credential collection/storage, HTTP-auth UI, manual authenticated-proxy configuration, automatic OS-proxy discovery or browser session forwarding in the current phase.** Keep the public/signed HTTP(S) core and its present rejection boundaries. There is no evidenced product requirement that justifies introducing these security-sensitive paths during release qualification. Existing environment-proxy behavior must be documented accurately: it is already inherited by reqwest, including environment URLs containing proxy Basic credentials; it is not a supported credential-management workflow.

The smallest recommended follow-up is to publish this decision and the environment-proxy inventory, retain the controlled fixture as regression evidence, and continue #46/#47/#89 qualification. No new implementation dependency is required. Revisit only for an explicit, scoped user need with a reproducible sanitized server/proxy case and acceptance of the threat model and tests below. A future Basic-auth slice would require a separate implementation issue; this decision does not authorize one or imply cookie support.

## Source observations and system-proxy inference

`Manager::open_with_ca` in `lib.rs` constructs one shared reqwest client with normal certificate verification, explicit timeouts, `referer(false)` and `redirect(Policy::none())`. It does **not** call `no_proxy()` or set an explicit proxy. reqwest's system matcher is therefore still enabled. Its `ClientBuilder::build` calls `ProxyMatcher::system()`, which delegates to hyper-util `Matcher::from_system()`.

In the inspected hyper-util implementation, `from_system()` always starts with the environment (`ALL_PROXY`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, with lowercase alternatives); Windows registry reading is behind `client-proxy-system`. That feature is absent in the inspected core build. **Inference from source plus build metadata:** this core inherits environment proxies, but Windows Internet Settings registry fallback is compiled out. Environment inheritance itself is confirmed by the fixtures above. It would be incorrect to promise that ZipZap follows the Windows Settings/WinHTTP/PAC/WPAD proxy configuration. This study did not toggle/read personal proxy settings or exercise an OS-discovery path; there is no claim of runtime qualification for those unsupported paths.

`validate_url` rejects user/password components on original and redirected download URLs. The custom `Manager::send` validates each joined redirect and rejects HTTPS downgrades. It changes the cloned request's URL and replays it; it does not strip headers based on origin changes. **Consequence for future auth:** reqwest automatic-redirect stripping cannot be relied on because ZipZap disabled that redirect policy. Adding Authorization at request construction without changing this loop would introduce a cross-origin leak. There is no such origin auth injection today.

Desktop enqueue and suggestions call the same Manager; native request schemas deny unknown fields and accept no arbitrary header/cookie/credential object. Browser/video actions do not gain credential rights from this study. No settings/job credential field, auth dialog, keychain integration or account logout mechanism currently exists.

The per-user SQLite job model intentionally stores URL/effective URL in plaintext. A signed URL is therefore already sensitive bearer data at rest, despite safe support-summary and error redaction. Windows user-file permissions protect it from other users under the current model; this is not an encrypted credential store or protection from a compromised same-user process. The study does not retrospectively promise encryption of existing signed-link history.

Windows Credential Manager is a viable platform primitive rather than a new storage subsystem. Its documented create/read/delete operations support an explicit per-user generic credential lifecycle, but error conditions (including absent logon credential set), opt-in persistence, UTF-16/secret buffer handling, removal failure and uninstall policy need actual Windows tests in the implementation slice. No vault access or API write was performed in this study. A generic cross-platform keychain dependency is unjustified for the Windows-only current product.

## Cookie/session decision is separate

**No-go:** browser cookie export, ambient browser/Windows login reuse, arbitrary Authorization headers, authenticated media/session extraction, OAuth login flows and account-token collection remain unsupported. Basic auth support would not imply consent to any of these. No new cookies, webRequest, history or broad-host network permissions are requested.

Any later cookie proposal needs its own explicit per-site purpose/consent and security decision covering HttpOnly/partitioned/SameSite semantics, origin/path/domain bounds, redirects, vault/lifetime/deletion, extension permission review and refusal/rollback tests. Copying a browser cookie is not a harmless synonym for supplying a public or signed URL. A public signed URL explicitly supplied by the user continues through the current Manager; expiry is handled by existing safe failure/link refresh, not credential/session harvesting.

## Dependencies, revisit gate and unknowns

#34 typed permanent authentication failure/no blind retry and #45 allowlisted diagnostics are the relevant completed foundations; reuse them. Metadata probes, ranges, resume, refreshed links, scheduled/retried jobs, desktop/manual/batch and native/browser enqueue must all share the eventual policy. #48/#50/#51 do not authorize auth support, and #49 is not an M6 blocker.

A scoped follow-up can be reconsidered when a concrete Basic-auth/proxy need is demonstrated, origin and proxy policies are independently chosen, the vault/forget/cancellation lifecycle above is accepted, and deterministic two-origin/TLS/proxy tests plus a Windows vault integration test are included. Until then no auth/proxy feature implementation is opened merely to keep the backlog busy.

Not checked: Windows registry proxy mutation/discovery, WinHTTP/PAC/WPAD, NTLM/Kerberos/Digest/OAuth, SOCKS, external corporate proxies, personal credentials, browser session extraction or Credential Manager writes. Any final changed candidate requires fresh local build verification; final product/release qualification is separate. Hosted GitHub checks were not started, following #54.
